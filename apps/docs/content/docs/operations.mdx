## Environment

The Elysia app reads environment variables at startup:

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | Local Compose PostgreSQL URL | PostgreSQL connection. |
| `PORT` | `3000` | HTTP listen port. |
| `TENANT_ID` | `local-dev` | Default development tenant. |
| `WORKSPACE_ID` | Empty | Optional default workspace. |
| `PLANET_SCHEMA` | `public` | Schema for Planet tables and SQL search path. |
| `EMBEDDING_DIMENSIONS` | `8` | Demo/API vector dimension. |
| `OPENAI_API_KEY` | Empty | Enables the OpenAI-compatible embedding provider. |
| `OPENAI_BASE_URL` | OpenAI API base URL | Optional compatible endpoint. |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | Embedding model name. |
| `LLM_API_KEY`, `LLM_API_URL`, `LLM_MODEL` | Empty | Optional entity extractor configuration; required in production. |
| `API_KEYS` | Empty | JSON map from bearer tokens to tenant/workspace scopes. |
| `OTEL_ENABLED` | `false` | Enables telemetry SDK initialization. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Empty | OTLP collector base URL. |
| `OTEL_SERVICE_NAME` | `unknown-planet-elysia` | Telemetry resource name. |

`NODE_ENV=production` requires API keys, an OpenAI embedding key, and all three LLM extractor settings. The application should use authenticated scope data; do not expose the development default tenant as a production authorization mechanism.

## Migrations

For local development, Compose initializes PostgreSQL with the ordered SQL files in `packages/postgres/migrations`. In production, the application owns the migration history and release step: add the required Planet storage SQL to the application's migration system and run it with your established PostgreSQL tooling. The package runner is available for local and direct maintenance use:

```sh
bun run --cwd packages/postgres migrate
```

Set `PLANET_SCHEMA` consistently for a single-schema setup, or use `PLANET_SCHEMAS` (comma-separated) with the package runner for multiple schemas. PostgreSQL vector search requires pgvector. Manage MongoDB collections and indexes through your application's MongoDB migrations. MongoDB transactions require a replica set; Atlas Vector Search also requires an index configured in Atlas. Neo4j constraints and indexes belong in application-owned Cypher migrations.

### Upgrade existing scope keys

PostgreSQL and MongoDB now use an unambiguous v2 storage key for `{ tenantId, workspaceId }`. This changes stored scope identifiers. **Stop all Planet writers and make a database backup before deploying the new readers.** Old and new application versions must not write to the same database during this migration.

For each PostgreSQL schema used by Planet, run the migration command. Migration `012` adds ingestion lease tokens and `013` inventories old scope keys in `unknownplanet_scope_key_map`. Migration `014` refuses to rewrite any key containing `:` until its tenant and workspace are specified. Inspect the inventory for each schema:

```sql
SELECT old_scope_id FROM planet.unknownplanet_scope_key_map WHERE tenant_id IS NULL;
```

Replace `planet` with your Planet schema. Supply the actual ownership for every listed key, then rerun the migration command:

```sql
UPDATE planet.unknownplanet_scope_key_map
SET tenant_id = 'acme', workspace_id = 'team:research'
WHERE old_scope_id = 'acme:team:research';
```

The old key alone cannot prove where its tenant ID ends and workspace ID begins. If two different scopes previously produced the same key, their rows are already mixed; inspect and separate those records from a backup before assigning a mapping. Migration `014` is transactional per schema and preserves the old-to-new map for rollback. To roll back after new writes, restore the backup; a simple key reversal cannot assign new records to legacy keys safely.

For MongoDB, call `migrateMongoScopeKeys(database, mappings, schemas)` from `@unknown-planet/mongodb` in a one-off maintenance process before starting the new application version. `mappings` maps each ambiguous old key to its real scope, for example `{ 'acme:team:research': { tenantId: 'acme', workspaceId: 'team:research' } }`. Pass the same `schemas` map used by `createMongoProvider`. The migrator inventories keys before writes, records mappings in `unknownplanet_scope_key_map`, and can resume after a partial failure. MongoDB transactions are required to move vector documents because their `_id` includes the scope key. Keep the backup until the migrated application has been checked.

## Authentication and isolation

When `API_KEYS` is unset, the sample API uses `TENANT_ID` and optional `WORKSPACE_ID` for every request. Configure `API_KEYS` as a JSON object mapping bearer tokens to scope objects to enable bearer authentication, for example:

```sh
API_KEYS='{"replace-with-secret":{"tenantId":"tenant-a","workspaceId":"workspace-a"}}'
```

Use secret management in deployed environments. The SDK expects the application to derive scopes from verified authentication context.

## Telemetry

Set `OTEL_EXPORTER_OTLP_ENDPOINT` or the standard traces/metrics endpoint variables to export telemetry over OTLP/HTTP. Set `OTEL_SDK_DISABLED=true` to disable SDK initialization. Instrumentation covers HTTP requests, SDK operations and stages, embedding/extraction calls, storage adapter calls, and PostgreSQL query duration/errors. Prompts, SQL text and parameters, credentials, and tenant IDs are not recorded.

## Local database lifecycle

Compose persists database data in named volumes. Migration files mounted into `/docker-entrypoint-initdb.d` run only when a new data directory is initialized. Recreating that volume deletes its local database contents; for an existing volume, apply migrations with the migration command instead.
