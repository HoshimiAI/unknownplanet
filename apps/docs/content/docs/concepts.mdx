## Planet client

`Planet` is the SDK facade. It exposes graph, vector, memory, document, evidence, identity, ingestion, blob, SQL, custom collection, and hybrid query APIs. It delegates operations to stores supplied through `PlanetConfig`.

```ts
import { Planet } from '@unknown-planet/sdk';
import { createPostgresProvider } from '@unknown-planet/postgres';

const provider = createPostgresProvider({ database: pool });
const planet = new Planet({
  providers: [provider],
  routing: {
    graph: 'postgres', vector: 'postgres', documents: 'postgres',
    chunks: 'postgres', evidence: 'postgres', memories: 'postgres',
    ingestionJobs: 'postgres', identities: 'postgres', sql: 'postgres',
  },
  scope: { tenantId: 'acme' },
  embeddings,
});
```

Only configure routes for capabilities present on the named provider. An unavailable capability raises a `PlanetCapabilityError` when used.

## Lifecycle hooks

Configure Planet-wide `hooks` to observe public feature operations. Callbacks run in registration order and are awaited; callback errors are ignored so they cannot change the operation result. Scoped clients and clients returned by `withRouting()` or `withProviders()` inherit the hooks.

```ts
const planet = new Planet({
  providers: [provider],
  hooks: [async (event) => {
    if (event.phase === 'failed') console.warn(event.operation, event.error?.name);
  }],
});
```

Each event has an `operation` name and a `phase` of `started`, `completed`, or `failed`. Completion and failure events include `durationMs`; failure events include an error name and, for `PlanetError` instances, a stable error code. Events do not include error messages, arguments, results, or tenant scope. Hooks observe SDK operations only; opaque methods on values returned by `planet.extension()` remain owned by the extension.

## Providers and routing

A `DataLayerProvider` has an `id` and can implement one or more contracts such as `graph`, `vector`, `memories`, or `blobs`. `ProviderRouting` maps each capability to a provider ID. This permits mixed backends, such as PostgreSQL for graph records and a dedicated vector service for embeddings.

Provider routing is explicit. Registering a store does not automatically route a capability when the application supplies a routing map. Routing policies can select providers dynamically for each operation.

## JSON validation schemas

`validationSchemas` validates JSON properties, metadata, and values on writes through the Planet SDK. It does not create or migrate PostgreSQL schemas, tables, columns, indexes, or MongoDB collections. The earlier `customSchemas` name remains a compatibility alias for this JSON validation only. It applies before a routed provider stores the data, including records generated by document and memory ingestion. Use `graph.node:<type>` or `graph.edge:<relation>` when fields belong to one graph type or relation; a plain `graph.node` or `graph.edge` schema applies to all of them.

```ts
const planet = new Planet({
  providers: [postgres],
  validationSchemas: {
    'graph.node:Person': {
      type: 'object',
      properties: { department: { type: 'string' } },
      required: ['department'],
    },
  },
});
```

Graph updates validate the complete properties value that will be stored. Developers own migrations and database structure for their application tables and collections. Planet can route SQL and registered MongoDB collection operations through `planet.custom.sql` and `planet.custom.collection`; it does not provision those structures. Custom queries do not receive automatic JSON validation or tenant filtering. Provider `schemas` select namespaces for Planet's built-in capabilities; `validationSchemas` validates JSON values. Calls made directly to a provider bypass Planet's validation. See [Custom application data](/docs/guides/custom-data) for setup and examples.

## Feature policy

Use `featurePolicy` to enable or disable SDK storage capabilities by tenant/workspace and operation. It is a synchronous application callback; returning `false` raises `PlanetFeatureDisabledError` (`feature_disabled`, HTTP 403). When omitted, all configured capabilities keep their normal behavior.

```ts
const planet = new Planet({
  providers: [postgres, qdrant],
  featurePolicy: ({ capability, operation, scope }) => {
    if (scope.tenantId === 'starter' && capability === 'vector') return false;
    if (scope.tenantId === 'read-only' && operation === 'write') return false;
    return true;
  },
});

const tenant = planet.withScope({ tenantId: 'starter', workspaceId: 'team-a' });
```

The policy runs before provider routing, so it applies regardless of which adapter serves a capability. Use it for product access and rollout rules. Authenticate the caller and derive scope in the application first; this callback does not receive user or role claims and is not a replacement for authorization. Direct calls to database clients outside the Planet SDK are not gated.

## Scope and tenant isolation

The SDK passes `PlanetScope` (`tenantId` and optional `workspaceId`) to scoped store calls. Create a request-specific client with `planet.withScope(...)` after authenticating the caller. The demo API accepts a single `TENANT_ID`/`WORKSPACE_ID`; when `API_KEYS` is configured, bearer tokens map to tenant scopes.

Scope isolation depends on every configured provider enforcing the scope it receives. Do not trust tenant IDs supplied by an unauthenticated caller.

## Embeddings

`EmbeddingProvider` converts text to numeric vectors. Planet uses it for semantic search, document and memory ingestion, and entity matching. Vector collections can constrain dimensions and model names at provider configuration time. Keep the provider model and dimensions consistent for every vector in a namespace.

The Elysia demo falls back to a deterministic character-hash embedding when `OPENAI_API_KEY` is absent. This validates storage flow but does not produce useful semantic embeddings. The SDK also exports `OpenAICompatibleEmbeddingProvider` for OpenAI-compatible endpoints.

## Errors

The SDK exports `PlanetError` and specialized capability, conflict, not-found, provider, and validation errors. The Elysia API maps errors to JSON containing an `error`, `code`, and `requestId`; ingestion failures may also include a `jobId`.
